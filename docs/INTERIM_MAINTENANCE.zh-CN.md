# 完整版本发布前，怎样分享中间进展

[English](INTERIM_MAINTENANCE.md) · [维护说明](../MAINTAINING.md)

有用的中间态更新要说清：现在能用什么、哪些变化已在限定范围内验证、还剩什么。
不必因此改包版本，也不必承诺下一个版本一定按预计时间发布。本页是维护文档，
不是新技能，也不改变六个可安装技能的调用策略。

## 一轮小而完整的维护

1. 核选定仓库的当前版本、相关CI和少量新增Issue/PR。先与上次已验基线比较，不重复已完成工作。
2. 研发比公开页面走得更远时，沿当前项目入口读取具名结果。没有新commit或任务消息安静，
   单独都不能证明没有进展。
3. 写带日期的四部分更新：当前可用版本、限定范围内完成项、未完证据/选择、下一步动作。
   已观察的事实与改进建议分开。
4. 只公开已经选定的内容。检查完成、定时任务运行或预计发布时间，本身不等于选择了
   push、Release、部署或更改调度。

定期执行时，明确周期、可写范围、证据预算、通知条件和停止条件；先手动运行一轮再安排定时。
除非维护者要求周期播报，普通在途状态保持安静，只通知真正需要处理的失败、完成或决定。
为下一轮保留最新基线与未完事项的恢复入口。

## 证据变化时，保持原来的适用范围

以下是合成示例，不代表某个真实产品的验收结论：

| 新观察 | 准确的维护记录 | 不能据此推出 |
| --- | --- | --- |
| 构造输入通过源码测试 | 该修订通过这份构造用例 | 所有真实调用者或成品都通过 |
| 真实调用者暴露失配 | 记录新红项、受影响输入和负责人，保留原范围的结果 | 原测试没有跑过，或原绿项可以冲掉新失败 |
| 窄修通过独立复核 | 对已审修订与输入关闭这项缺陷 | 安装、实际运行或整个版本都已完成 |
| 维护者后移一项窄兼容改动 | 记录所选延期与恢复条件 | 行为已通过，或其它问题也一并延期 |

通知前先把后来结果与同一主体、同一阶段对齐。原失败和修订结果都保留，不因消息晚到就重跑
完成的检查。一次事故可以形成候选，不自动成为通用规则或新增发布门。已选验证可使用
[verify-claim](../skills/verify-claim/SKILL.md)，真正未决的范围选择可使用
[intent-checkpoint](../skills/intent-checkpoint/SKILL.md)。

## 分享可读结论，保留恢复证据

公开说明可以写用户价值、验证范围、限制和当前支持版本；不放入私密请求、凭据、客户记录或
运维细节。内部仍保留恢复工作所需的证据；从公开页面省去细节，不等于删除内部恢复链。

配套项目的真实、明确未完成的中间态示例见
[研发进展](https://github.com/SeasonCake/bidking-inference/blob/main/docs/DEVELOPMENT_STATUS.zh-CN.md)。
